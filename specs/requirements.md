# Requirements Document

## Introduction

`task-linear-sync` is a reusable, publishable npm library and CLI that maintains bidirectional “golden thread” traceability between repository specification tasks defined by supported spec-driven development frameworks and issues in a Linear workspace. The supported frameworks are BMAD, GitHub SpecKit, open-spec, and Kiro, plus a generic Markdown fallback for repositories that use task-shaped Markdown files without a framework-specific layout. The tool discovers actionable task headings and checkboxes across a repository using framework adapters, matches them to existing Linear issues with a weighted scoring model and a globally optimal one-to-one assignment, creates missing issues, sets each issue’s description to mirror the task’s repository content (`Task_Body`), screened before propagation, persists machine-readable sync state, including the durable task identity, in a Linear attachment on each issue, reconciles workflow state and checkbox completion, and writes the visible issue-reference prefix back into the Markdown while the durable identity anchor lives in the Linear attachment metadata.

This is a **standalone specification** for the tool as a publishable library that follows an **intelligent-defaults, overridable-via-configuration** model. The library ships **sensible built-in defaults** for every value that admits a reasonable generic default — framework adapters, task-file patterns, specification base directories, task-heading grammar, phase/summary/rollup patterns, skip directories, scoring weights and confidence thresholds, retry/backoff limits, timeouts, credential environment-variable names, and the tool-identity values derived from a configurable `toolId` — and applies each default when the consumer does not override it. Every default is overridable through configuration.

Only values that are intrinsically tied to a specific workspace and cannot carry a meaningful generic default MUST be supplied by the consumer: **one or more issue-tracker team identities** (a single Linear workspace may span multiple teams in an enterprise monorepo, so path prefixes route to both a team key and a project via `{teamKey, project}` pairs, with a configurable default team and default project for unrouted paths), the **project identities / mapping targets** for each configured team, and the **workflow state identities** for each configured team. The **confirmation key** defaults to a generic overridable placeholder value and is never validated against any constant.

Two properties are load-bearing throughout: **Safety first** (read-only commands never mutate; mutating commands require explicit confirmation gates; propagated text is screened for secrets and PII; state lives outside the repository with owner-only permissions; by default applied runs are journaled to an encrypted, resumable audit manifest, while the audit manifest and its encryption are each independently configurable and MAY be disabled — disabling the audit manifest removes the resumable-rollback capability, and disabling only its encryption persists the manifest unencrypted) and **Durable identity** (each task has a deterministic `Stable_UUID` derived from its stable positional seed; the durable identity anchor is carried in the machine-readable metadata of a tool-managed Linear attachment addressed by a deterministic idempotent URL, rather than in the issue description; the visible issue prefix written into the Markdown line is the human-readable reference to the created Linear issue; matching prefers the durable attachment identity so re-runs are idempotent and renames/moves do not orphan issues). The attachment itself is always visible in Linear as a link with a deliberately innocuous title and subtitle; its metadata is best-effort hidden and MUST NOT be relied upon as permanently invisible, since Linear exposes metadata through the API and may surface it in the UI in the future.

The library ships no real organization identifiers, tokens, or UUID values as defaults: the required identity values (team, projects, workflow states) have no built-in default at all, and the placeholder confirmation key and `toolId` are generic conventions rather than organization-specific literals.

In addition to the sync library and CLI, the library ships an **optional web component** (the `Sync_History_Server`), built on Next.js and React, that serves the same `Attachment_URL` scheme (`<configured-base-host>/<toolId>/<task-uuid>`) the sync engine already writes into Linear, resolving each such URL to a human-readable **sync-history** page for that task. The web component reads history live per request from the Linear `Sync_Attachment` metadata (never from the encrypted local audit manifest or `State_Directory`), exposes only security-screened, human-readable data to the browser, keeps Linear credentials server-side only, defaults to private (authenticated) access with opt-in public access, and delivers near-realtime updates through a tiered transport that prefers Server-Sent Events and always falls back to periodic polling so the app runs on serverless, edge, containerized Node, and traditional Node hosts. The web component is additive: it MAY depend on existing sync capabilities but does not remove or replace them.

The library additionally ships an **optional embedded Model Context Protocol (MCP) server** (the `MCP_Server`), exposed as a package subpath entry point (default `<pkg>/mcp`), that lets AI coding agents (for example Claude Code, Cursor, Windsurf, and Kiro IDE agents) drive the sync engine programmatically instead of shelling out to the CLI. The `MCP_Server` is an additional optional **interface layer** alongside the existing CLI binary and background worker: it routes tool calls directly into the same core engine API (`buildSyncPlan` and `applySyncPlan`) and enforces the same underlying safety, confirmation, locking, journaling, and screening guarantees the CLI enforces. It exposes read-only tools that never mutate, and a mutating apply tool that is opt-in (disabled by default), gated by the confirmation key and an accept-low-confidence argument, and additionally requires a fresh, valid plan reference. The `MCP_Server` runs over stdio by default and optionally over an HTTP/SSE transport for remote use; when the network transport is enabled it keeps Linear credentials and auth tokens server-side. The `MCP_Server` is additive: it MAY depend on existing sync capabilities but removes or replaces none of them.

The library additionally ships an **optional official GitHub Action** (the `CI_Enforcement_Action`, published as `task-linear-sync-action`) that provides a **CI/CD enforcement layer** wrapping the CLI’s strictly read-only `check` and `plan` commands. Enterprise teams use the action to verify, before a pull request merges, that repository tasks are synchronized with Linear: the action consumes the sanitized read-only plan/check output and fails the pipeline build when configurable violation conditions are detected (unmapped high-confidence tasks, unresolved conflict blocks on protected branches, or spec-vs-Linear drift). The action performs zero Linear mutation requests and zero repository file writes, needs only a read-scoped Linear credential supplied through the CI environment, never exposes that credential, and emits only security-screened, human-readable summaries. The `CI_Enforcement_Action` is additive: it wraps the same published CLI rather than reimplementing engine logic, and it removes or replaces none of the existing capabilities.

The library is delivered with **comprehensive documentation** covering installation, configuration, and at least one usage scenario for every surface (the core sync library and CLI, the programmatic API, the background worker and hook triggers, the `Sync_History_Server` web component, the `MCP_Server`, and the consumer-facing `CI_Enforcement_Action`), a **full test strategy** organized as a test pyramid across all surfaces (with property-based, contract, and security tests as required cross-cutting types layered on the correctness-property methodology the spec already mandates), and the project’s **own CI/CD automation** (the `Project_CICD_Pipeline`) that builds, lints, type-checks, tests, and releases the utility itself. The `Project_CICD_Pipeline` is the project’s internal build/test/release automation and is distinct from the consumer-facing `CI_Enforcement_Action` of Requirement 26.

## Glossary

- **Framework**: A supported spec-driven development method or repository convention. The built-in frameworks are `bmad`, `spec-kit`, `open-spec`, `kiro`, and `generic`.
- **Framework_Adapter**: A component that maps a framework’s repository conventions to the canonical task model used by `task-linear-sync`. An adapter may define task-file patterns, base directories, framework detection rules, `Feature_Name` extraction rules, task-heading grammar, phase/summary/rollup patterns, sibling document names, title behavior, and optional agent-hook templates.
- **Supported_Framework**: One of `bmad`, `spec-kit`, `open-spec`, `kiro`, or `generic`.
- **Framework_Preset**: A built-in `Framework_Adapter` shipped with the tool for a supported framework.
- **Framework_Id**: The canonical identifier recorded for a discovered task file or task, one of `bmad`, `spec-kit`, `open-spec`, `kiro`, or `generic`.
- **Framework_Metadata**: Machine-readable framework context persisted with sync state, including at least `Framework_Id`, `Feature_Name`, repository-relative task file path, and `Local_Task_ID` where present.
- **Task**: An actionable unit extracted from a supported task file, either a heading task or a checklist task.
- **Task_File**: A Markdown file whose basename matches the configured task-file patterns and which is treated as a source of tasks by the active `Framework_Adapter`.
- **Heading task**: A Markdown heading whose text matches the configured heading-id grammar (which has a built-in default and is overridable).
- **Checklist task**: A Markdown checkbox item (`- [ ]` / `- [x]`).
- **Local_Task_ID**: A framework- or author-supplied task identifier parsed from a heading or checklist line, such as `Task 1.2`, `T001`, `TASK-1`, `FOUND-1`, or another configured identifier.
- **Specs_Base_Directories**: The configured list of base directories beneath which feature specification folders may reside. Built-in defaults include `.kiro/specs/`, `specs/`, `spec/`, `openspec/`, `open-spec/`, `bmad/`, `bmad-method/`, and `docs/`, all overridable.
- **Specs_Base_Directory**: Any single configured entry in `Specs_Base_Directories`.
- **Feature_Name**: The framework-adapter-derived feature, story, change, or capability name associated with a task file. For common layouts this is the immediate parent directory name of a task file beneath a configured `Specs_Base_Directory`, or the next meaningful segment after a framework marker such as `changes/` or `specs/`. Absent when no feature segment can be derived.
- **Team_Key**: A configured Linear team identity (team key) that path prefixes and issues are scoped to. A single Linear workspace MAY have one or more configured `Team_Key`s; each configured team carries its own project identities and workflow state identities. There is no built-in default `Team_Key`.
- **ProjectByPath**: The consumer-supplied map from a repository path prefix to a `{teamKey, project}` pair, resolved by longest-matching character-length prefix with a deterministic tie-break. Each entry MUST specify both a `Team_Key` and a project (the project-only shape is not supported). Paths matching no configured prefix fall back to the configurable default team and default project.
- **Stable_UUID**: A deterministic RFC-4122 version-5-shaped UUID derived from a task’s stable positional seed, serving as the task’s derived identity. The seed includes framework identity, feature identity, and a stable local task identifier where present, or a stable ordinal fallback where no local identifier exists. It is used as the task UUID before a Linear issue and `Sync_Attachment` exist and to seed the `Sync_Attachment` metadata identity anchor on first creation. It is not persisted as an in-file marker.
- **Issue_Prefix**: A visible `[<KEY>-<N>]` token in Markdown identifying the associated Linear issue, where `<KEY>` is the consumer-configured confirmation key. It is the human-readable in-file reference to the associated Linear issue.
- **Task_Body**: The repository-side content that mirrors the Linear issue description. It is the task’s heading or line PLUS all Markdown beneath it up to (but not including) the next task or the next sibling-or-shallower heading, INCLUDING nested checklist children. It is a multi-line “task section” of the spec file.
- **Managed_Description_Block**: The entire tool-managed Linear issue description, which mirrors the task’s `Task_Body`. It has no delimiters and no human-authored prefix carve-out; the whole description is owned by the tool and reconciled under the Requirement 9 conflict machinery. The durable task identity lives in the `Sync_Attachment` metadata, not in the description.
- **Sync_Attachment**: The Linear attachment the tool creates or updates on an issue to persist machine-readable sync state. It is identified idempotently by its `Attachment_URL` on that issue, is always visible in Linear as a link bearing a deliberately innocuous title and subtitle, and carries the `Sync_State_Payload` in its `Attachment_Metadata` whose visibility is best-effort hidden and not guaranteed. A task’s append-only history MAY span a chain of paged attachments — a page-0 canonical `Sync_Attachment` addressed by the `Attachment_URL` plus zero or more `Continuation_Attachment`s addressed by `Continuation_Attachment_URL`s — while the page-0 canonical `Sync_Attachment` always holds the durable identity anchor and remains the sole identity anchor for matching.
- **Attachment_Metadata**: The JSONObject carried on the `Sync_Attachment`. Metadata values are strings or numbers only; any nested or complex sync state is serialized into a single string value stored under the `Metadata_Namespace_Key` rather than relying on deep nesting.
- **Metadata_Namespace_Key**: The single custom top-level key within `Attachment_Metadata` (default derived from the configurable `toolId`; overridable) under which the serialized `Sync_State_Payload` is stored. The `Metadata_Namespace_Key` MUST NOT collide with Linear reserved rich-render metadata keys (`title`, `messages`, `attributes`).
- **Attachment_URL**: The deterministic idempotent URL of the form `<configured-base-host>/<toolId>/<task-uuid>` that serves as the per-issue idempotency key for creating or updating the page-0 canonical `Sync_Attachment`. The base host, the `toolId` segment, and the full template are overridable, and the base host has a benign placeholder default carrying no real organization identifier. The `Attachment_URL` addresses page 0, the canonical `Sync_Attachment` that holds the durable identity anchor and is the sole identity anchor for matching; later pages of the append-only history live on `Continuation_Attachment`s addressed by `Continuation_Attachment_URL`s of the form `<base-host>/<toolId>/<task-uuid>/<pageN>`.
- **Sync_State_Payload**: The machine-readable sync state serialized into the `Attachment_Metadata` under the `Metadata_Namespace_Key`, including the durable task UUID (the identity anchor), `Framework_Metadata`, the managed-description content hash, checkpoint references, sync cursors or timestamps as applicable, and the `Sync_History_Log`. The `Sync_State_Payload` does NOT replace the local `Checkpoint`: it carries a durable identity anchor, framework context, and content hash on the Linear side, while the local `Checkpoint` / `sync-state.json` remains the authoritative local state store per Requirement 11.
- **Sync_History_Event**: A single ordered, timestamped, human-readable, security-screened record of a sync action affecting a task (for example: task discovered, issue created, task matched to issue, title updated, managed description updated, checkbox or workflow state changed, conflict detected, or `rollback`). Each `Sync_History_Event` carries a machine-readable event kind, a human-readable timestamp, and a human-readable, screened description. A `rollback`-kind event records that a prior run was reverted and references the sync action or actions it reverses, rather than deleting or rewinding any earlier entry. Once appended, a `Sync_History_Event` is immutable: it is never modified or deleted.
- **Sync_History_Log**: An append-only, chronologically ordered, complete log of `Sync_History_Event` entries carried within the `Sync_State_Payload`. Entries are only ever appended; previously-recorded entries are never modified or deleted, and a rollback is recorded as a new `rollback` event rather than by removing or rewinding earlier entries. Entries use a compact, storage-efficient encoding so that more history fits within a single attachment’s metadata. Because `Attachment_Metadata` values are strings or numbers only, the `Sync_History_Log` is serialized into the single string value stored under the `Metadata_Namespace_Key` of the current page attachment, together with the rest of the `Sync_State_Payload`, rather than as a nested metadata object. When the current page attachment approaches the configurable per-page rollover threshold (`History_Log_Max_Entries`) or the practical attachment metadata size limit, history continues in a new deterministic paged `Continuation_Attachment` so that the complete history is preserved, unbounded, across the attachment chain.
- **History_Log_Max_Entries**: The configurable per-attachment-page capacity / rollover threshold — the maximum number of `Sync_History_Event` entries stored in a single page attachment before appended history rolls over to the next deterministic paged `Continuation_Attachment` (default 50; overridable; a size-based per-attachment threshold MAY additionally trigger rollover). `History_Log_Max_Entries` is NOT a global truncation cap: no entry is ever dropped, and the total retained history is unbounded across the attachment chain.
- **Continuation_Attachment**: A `Sync_Attachment` addressed by a deterministic `Continuation_Attachment_URL` that holds a later page of the append-only `Sync_History_Log` for a task. Continuation attachments are history-only: they carry additional `Sync_History_Event` pages but are not used for durable-identity matching. Page 0 is the canonical `Attachment_URL` and remains the identity anchor; continuation pages are indexed from 1 upward.
- **Continuation_Attachment_URL**: The deterministic paged URL of the form `<configured-base-host>/<toolId>/<task-uuid>/<pageN>`, where `<pageN>` is a page index incrementing from 1, that addresses a `Continuation_Attachment` on an issue. It is derived from the same configured base host and `toolId` as the canonical `Attachment_URL`, its template is overridable consistent with the `Attachment_URL` template, and its base host carries the same benign placeholder default carrying no real organization identifier. The page-0 canonical `Attachment_URL` (`<base-host>/<toolId>/<uuid>`) is the identity anchor; `Continuation_Attachment_URL`s are used only to preserve later pages of the append-only history.
- **Sync_History_Server**: The optional Next.js and React web component that serves the `Attachment_URL` scheme `<configured-base-host>/<toolId>/<task-uuid>`, resolving each such URL to a human-readable sync-history page rendered from the `Sync_History_Log` read live from the Linear `Sync_Attachment` metadata. Also referred to as the Web_App.
- **Access_Control_Mode**: The configurable access mode governing who may read a sync-history page, one of `private` (default; requires a valid bearer token or session) or `public` (opt-in; readable by anyone holding the URL).
- **Realtime_Transport**: The tiered mechanism by which the `Sync_History_Server` delivers near-realtime updates to the browser, preferring Server-Sent Events (SSE) where the hosting environment supports long-lived responses and falling back to periodic HTTP polling where it does not.
- **Web_Auth_Token**: The bearer token, read server-side from a configurable environment variable whose name is derived from the `toolId`, that a client presents to view a sync-history page while the `Access_Control_Mode` is `private`.
- **MCP_Server**: The optional embedded Model Context Protocol server module, shipped inside the published package as the `<pkg>/mcp` subpath entry point, that exposes the sync engine to AI coding agents as an alternative interface layer alongside the CLI binary and background worker, routing tool calls into the same core engine API (`buildSyncPlan` and `applySyncPlan`) and enforcing the same safety, confirmation, locking, journaling, and screening guarantees as the CLI.
- **MCP_Tool**: A single callable tool exposed by the `MCP_Server`. Read-only MCP_Tools (`task_sync_plan`, `task_sync_status`, `task_sync_inventory`) never mutate, issue no Linear mutation request, and perform no repository write; the mutating MCP_Tool (`task_sync_apply`) applies a sync plan and is opt-in, gated, and disabled by default.
- **Plan_Reference**: The identifier or hash of a sync plan produced by a prior `task_sync_plan` MCP_Tool call, required as an argument to `task_sync_apply`. A `Plan_Reference` is valid only WHERE it matches a plan the `MCP_Server` produced and that plan’s stability guards (the input file content hashes and the version-control HEAD commit identifier of Requirement 12, criteria 2 and 3) still hold; otherwise it is treated as unknown or stale.
- **CI_Enforcement_Action**: The optional official GitHub Action, published as `task-linear-sync-action`, that wraps the CLI’s strictly read-only `check` and `plan` commands (Requirement 15) and the sanitized plan review report (Requirement 16) to enforce task-to-Linear synchronization in CI/CD pipelines. It performs zero Linear mutation requests and zero repository file writes, derives its violation determinations solely from the sanitized read-only plan/check output, and fails the pipeline build when one or more of its enabled failure conditions are triggered.
- **Protected_Branch_Set**: The configurable set of branch names or patterns against which the `CI_Enforcement_Action` treats a run as targeting a protected branch; it defaults to the pull request’s base/target branch when unset.
- **Agent_Hook**: A framework- or IDE-provided hook definition that can invoke the tool’s shell-invocable enqueue entry point to trigger a sync on an external event. The built-in Kiro adapter uses `.kiro/hooks/*.json` files whose `command` action can invoke the enqueue entry point.
- **Agent_Hooks_Directory**: The directory beneath the repository root where agent-hook definition files reside. The default is framework-specific: `.kiro/hooks/` for the Kiro adapter and `.task-linear-sync/hooks/` for the generic adapter; overridable.
- **Enqueue_Command**: The stable shell-invocable entry point (a CLI subcommand or npm script) that enqueues a non-blocking sync; usable by git hooks, agent hooks, CI, or manual invocation.
- **Checkpoint**: Persisted per-task state (`sync-state.json`) recording last-known checked state, title, issue update time, issue state, and description (`Task_Body`) content hash.
- **Audit_Manifest**: An optional (enabled by default), resumable record of an applied run sufficient to fully roll it back, encrypted by default with independently configurable encryption. WHERE the audit manifest is disabled, no manifest is written, no run journaling occurs, and the resumable rollback capability is unavailable; WHERE the audit manifest is enabled but its encryption is disabled, the manifest is persisted unencrypted. The encryption flag is only meaningful when the audit manifest is enabled.
- **Create_Intent**: A persisted record tracking the lifecycle of a single issue-creation attempt.
- **Confidence**: A band assigned to a match: `high`, `medium`, `low`, or `unmatched`.
- **Match_Margin**: The distance in score between a chosen match and its nearest competitor (from both task and issue sides).
- **Bootstrap_Mode**: The repository-authoritative sync mode used when no checkpoint exists. `Bootstrap_Mode` has its own independently configurable conflict-action map from `Description_Conflict_Type` to `Conflict_Action`.
- **Sync_Mode**: The reconciliation mode used when a checkpoint exists. `Sync_Mode` has its own independently configurable conflict-action map from `Description_Conflict_Type` to `Conflict_Action`, distinct from the `Bootstrap_Mode` map.
- **Description_Conflict_Type**: One of `linear-changed` (the Linear issue description changed since the checkpoint and the task’s `Task_Body` did not), `spec-changed` (the task’s `Task_Body` changed since the checkpoint and the Linear issue description did not), or `both-changed` (both changed since the checkpoint), determined against the checkpoint for a matched task’s Linear issue description versus its `Task_Body`, where “changed” and “difference” mean a `Meaningful_Diff` per Requirement 9, criterion 21. In `Bootstrap_Mode`, where no checkpoint exists, any `Meaningful_Diff` between the task’s `Task_Body` and Linear’s current description is resolved through the `Bootstrap_Mode` conflict-action map.
- **Meaningful_Diff**: A difference between the Linear issue description and the task’s `Task_Body` that persists after both sides are normalized by the configured `Description_Normalization_Profile`. Insignificant formatting-only differences that do not persist after normalization (for example trailing whitespace, blank-line runs, or line-ending style introduced by issue-tracker Markdown round-tripping) are NOT meaningful diffs and SHALL NOT trigger a `Description_Conflict_Type` classification, any `Conflict_Action`, a Linear description write, or a `Conflict_Markers` write.
- **Description_Normalization_Profile**: The configurable set of normalization rules, with a sensible built-in default, applied identically to both the Linear issue description and the task’s `Task_Body` before they are compared, so that the comparison is symmetric and only `Meaningful_Diff`s are detected. It is tool-agnostic; the concrete canonicalization is a design decision.
- **Conflict_Action**: One of `overwrite-linear`, `overwrite-spec`, `report-only`, `skip`, `prefer-newer`, or `fail` — the resolution applied to a managed-description conflict of a given `Description_Conflict_Type`, modeled on git merge/conflict-resolution semantics.
- **Conflict_Markers**: Git-style merge conflict markers written into a task’s `Task_Body` region in the spec file by the `overwrite-spec` action — a start line `<<<<<<< spec (local)`, a `=======` separator, and an end line `>>>>>>> linear (remote)` — enclosing the local `Task_Body` content (between the start line and the separator) and Linear’s current description content (between the separator and the end line) so a human can resolve the conflict in place. A `Task_Body` region containing `Conflict_Markers` is an `Unresolved_Conflict_Block`.
- **Unresolved_Conflict_Block**: A task’s `Task_Body` region in a spec file that still contains `Conflict_Markers`, i.e. a conflict a human has not yet resolved.
- **State_Directory**: The location, outside the repository, where the tool stores manifests, checkpoints, intents, reports, and locks.
- **Confirmation_Key**: The key value required by `--confirm-team` and used in issue prefixes; it has a generic overridable built-in default (`SYNC`) and is never validated against any constant.
- **Linear_Port**: The interface abstracting all Linear GraphQL access, injectable for testing or custom transport.
- **Security_Screener**: The component that redacts secrets and PII from propagated text and from reports/logs.
- **Managed_Git_Hook**: A git client-side hook (default set: `pre-push`, `post-merge`; configurable to any valid git hook names) that the tool installs a managed, non-blocking block into to enqueue a sync.
- **Test_Pyramid**: The layered test strategy the project follows: a broad base of fast unit tests over the pure core logic, a middle layer of integration tests exercising component interactions through an injected fake `Linear_Port`, and a thin top layer of end-to-end/system tests over each user-facing surface, augmented by property-based tests, contract/port tests, and security tests as required cross-cutting test types.
- **Project_CICD_Pipeline**: The project’s own continuous-integration and release automation, implemented as GitHub Actions workflows, that builds, lints, type-checks, tests, and releases the `task-linear-sync` utility itself across all its surfaces. The `Project_CICD_Pipeline` is distinct from the consumer-facing `CI_Enforcement_Action` of Requirement 26: the `CI_Enforcement_Action` is a published artifact that consumers add to their own pipelines to enforce sync state, whereas the `Project_CICD_Pipeline` is the internal automation that validates and publishes this project.
- **System**: The `task-linear-sync` library and CLI as a whole.

## Requirements

### Requirement 1: Multi-framework repository task discovery

**User Story:** As a developer using BMAD, GitHub SpecKit, open-spec, Kiro, or generic Markdown task files, I want the tool to find all specification task files in my repository safely, so that every actionable task can be traced without escaping the repository sandbox.

#### Acceptance Criteria

1. WHEN discovery is invoked with a repository root, THE System SHALL canonicalize the root to an absolute path with symbolic links and relative segments resolved, and recursively locate every regular file whose basename matches the configured task-file patterns (default `tasks.md` and `TASKS.md`; overridable) beneath it, traversing to unlimited directory depth.
2. IF the provided repository root does not exist, is not a directory, or is not readable, THEN THE System SHALL abort discovery, perform no file reads, and report an error identifying the invalid root and the failing condition.
3. WHILE walking the repository tree, THE System SHALL skip every directory whose name matches the configured skip set (default `.git`, `node_modules`, `dist`, `.next`, `coverage`, and the tool state directory; overridable) and SHALL NOT descend into or include the contents of any skipped directory.
4. WHILE walking the repository tree, THE System SHALL neither traverse symbolic-linked directories nor include symbolic-linked files, and SHALL exclude such entries from results without aborting the walk.
5. IF a discovered task-file path resolves outside the canonicalized repository root, THEN THE System SHALL exclude it from results, perform no read of it, and report an error identifying the excluded path and indicating it escapes the repository root, while continuing discovery of remaining files.
6. WHEN discovery completes, THE System SHALL return repository-relative POSIX paths sorted in a deterministic lexicographic order that is byte-for-byte identical across repeated runs over an unchanged tree.
7. WHEN discovery finds no matching task files, THE System SHALL return an empty result and SHALL NOT report an error.
8. WHEN a task file is discovered, THE System SHALL associate it with a `Framework_Id` per Requirement 7 and SHALL locate its sibling specification documents (default `requirements.md`, `spec.md`, `plan.md`, `design.md`, and `architecture.md`, configurable, resolved in the same directory as the task file) as associated sibling specification documents when present, and SHALL omit any sibling that is absent without reporting an error.
9. WHEN reading any repository file, THE System SHALL confirm the resolved absolute path is inside the canonicalized repository root before opening it, and IF the resolved path is outside the root, THEN THE System SHALL refuse the read and report an error identifying the path.
10. WHEN repository version-control metadata is requested, THE System SHALL return the HEAD commit identifier, the current branch name, and the origin remote URL, omitting individually any value that is unavailable and returning the remaining available values without failing.

### Requirement 2: Framework-aware Markdown task parsing

**User Story:** As a developer, I want task files parsed into structured tasks with stable identities across BMAD, GitHub SpecKit, open-spec, Kiro, and generic Markdown conventions, so that headings and checkboxes map reliably to issues across edits.

#### Acceptance Criteria

1. WHILE parsing lines located between a fenced-code-block opening delimiter and its matching closing delimiter, THE System SHALL treat those lines as non-task text and SHALL exclude them from task extraction.
2. WHEN a heading’s text matches the configured heading-id grammar for the task’s active framework adapter (default: a case-insensitive leading identifier matching `(?:[A-Z][A-Z0-9_]{1,8}-\d+(?:\.\d+)?|Task\s+\d+(?:\.\d+)?|T\d{2,5})`, optionally followed by `: <title>` or whitespace `<title>`; overridable), THE System SHALL classify the heading as a heading task and record its 1-based line number.
3. WHEN a line matches the Markdown checkbox grammar (an optionally indented list marker followed by a bracketed state box), THE System SHALL classify the line as a checklist task subject to the exclusion rules in criteria 6 and 7.
4. WHEN parsing checklist tasks, THE System SHALL normalize leading indentation by mapping each tab to the configured tab width (default 2 spaces; overridable) and SHALL establish parent/child relationships using an indent-based stack, attaching each checkbox to the nearest checkbox at a strictly smaller normalized indentation, or to the enclosing heading task when no such checkbox exists.
5. WHILE parsing, THE System SHALL track the current phase as the text of the most recent heading matching the configured phase pattern (default: case-insensitive `(?:phase|story|milestone)\s+\d+`; overridable), defaulting to no phase before the first such heading.
6. WHEN a heading matches the configured summary-section pattern (default: a case-insensitive match at heading level 1 or 2 of any of `success criteria summary`, `summary`, `timeline estimate`, `risk management`, `next steps`, `acceptance criteria summary`, or `definition of done`; overridable), THE System SHALL exclude that section’s items from task extraction until the next heading of equal or shallower level, and SHALL record each excluded item with its 1-based line number and an exclusion reason indicating a summary section.
7. WHEN a line matches the configured rollup-label pattern (default: a bold-label line matching case-insensitively `**…completion checklist…**`, `**…success criteria summary…**`, or `**…definition of done…**`; overridable), THE System SHALL exclude every subsequent checkbox belonging to that rollup and SHALL record each excluded item with its 1-based line number and an exclusion reason indicating a rollup.
8. WHERE a document matches the configured flat-checklist detection markers (default: the path-marker list is empty, so a document is treated as flat only when it contains no heading matching the heading-id grammar; overridable) OR contains no heading matching the heading-id grammar, THE System SHALL treat top-level checkboxes as valid tasks without an enclosing heading.
9. WHEN parsing a task line, THE System SHALL parse no in-file identity marker and SHALL derive the task’s `Stable_UUID` per criterion 11.
10. WHEN a task line contains a visible issue prefix in the form `[<KEY>-<N>]` where `<KEY>` equals the configured confirmation key and `<N>` is one or more decimal digits, THE System SHALL parse the issue identifier.
11. WHEN parsing a task, THE System SHALL derive a deterministic `Stable_UUID` from the task’s stable positional seed, shaped as an RFC-4122 version-5 UUID, such that identical inputs reproduce a byte-for-byte identical UUID across runs; the stable positional seed SHALL include `Framework_Id`, `Feature_Name` when present, and `Local_Task_ID` when present, and SHALL fall back to a stable task ordinal and task-file identity when no `Local_Task_ID` is present, while excluding the visible issue prefix, checkbox state, and mutable title text.
12. WHEN parsing a heading or checklist line, THE System SHALL parse a `Local_Task_ID` when the configured identifier grammar matches at the beginning of the task title, and SHALL record the parsed `Local_Task_ID` on the task.
13. WHEN two or more tasks within a single file share the same local task ID, THE System SHALL emit a warning identifying the shared ID and the 1-based line numbers of all occurrences.
14. WHEN two or more tasks within a single file share the same issue reference, THE System SHALL emit a warning identifying the shared reference and the 1-based line numbers of all occurrences.
15. WHEN parsing a task file, THE System SHALL determine the task file’s `Feature_Name` using the active `Framework_Adapter` per Requirement 7, and SHALL record no `Feature_Name` when the adapter cannot derive one.
16. WHEN parsing a task whose `Task_Body` region contains `Conflict_Markers`, THE System SHALL flag the task as carrying an `Unresolved_Conflict_Block` and record that state on the task so that downstream reconciliation skips the task per Requirement 9.
17. WHEN parsing a task, THE System SHALL determine the task’s `Task_Body` extent as the task’s heading or line together with all Markdown content beneath it up to but not including the next task or the next heading of equal or shallower level, including nested checklist children, and SHALL record that `Task_Body` region on the task for description mirroring and conflict reconciliation per Requirements 9 and 10.

### Requirement 3: Markdown rendering

**User Story:** As a developer, I want the issue reference and status written back into my task files, so that the mapping is durable and my task files reflect issue state.

#### Acceptance Criteria

1. WHEN rendering a task file from an assignment map, THE System SHALL rewrite each assigned task line to include, in order, the configured issue-key prefix in the format `[<issue-key>]` and the desired title, preserving the line’s original leading indentation and, for heading lines, its original heading level, and SHALL preserve a present `Local_Task_ID` unless configured otherwise.
2. WHEN rewriting an assigned line, THE System SHALL set the desired title to the assignment’s provided title after removing configured title prefixes, redundant leading issue prefixes, and a duplicate leading local-task-identifier prefix only when the preserved line already carries that identifier, or, WHERE the assignment provides no title, THE System SHALL retain the line’s existing title unchanged.
3. WHEN rewriting an assigned checklist line, THE System SHALL set the checkbox state to the assignment’s provided checkbox state, or, WHERE the assignment provides no checkbox state, THE System SHALL retain the line’s existing checkbox state.
4. WHILE rendering multiple assigned task lines, THE System SHALL process lines in order of descending line number (bottom to top) so that all line indices remain valid throughout rewriting.
5. WHEN rendering a task file, THE System SHALL reproduce the file’s original trailing-newline style, emitting exactly one trailing newline WHERE the original content ended with a newline and emitting no trailing newline otherwise.
6. WHERE a line has no assignment in the assignment map, THE System SHALL leave that line byte-identical to its original content.
7. IF an assigned line cannot be matched to its expected heading or checklist structure, THEN THE System SHALL halt rendering of that file, retain the file’s original content unmodified, and return an error identifying the file path and line number.
8. WHERE a task carries an `Unresolved_Conflict_Block`, THE System SHALL leave that task’s `Task_Body` region containing `Conflict_Markers` byte-for-byte unchanged during rendering, SHALL NOT rewrite, nest, or strip its `Conflict_Markers`, consistent with the skip-and-report behavior of Requirement 9.

### Requirement 4: Path-to-team-and-project routing

**User Story:** As a maintainer of an enterprise monorepo spanning multiple Linear teams and multiple spec-driven frameworks, I want tasks routed to both a Linear team and a Linear project by their file path, so that traceability aligns with my repository layout across teams without hardcoding.

#### Acceptance Criteria

1. WHEN resolving a task’s routing target, THE System SHALL match the task’s file path against the consumer-supplied `ProjectByPath` map of path prefix to `{teamKey, project}` pair and select the entry whose matching prefix has the greatest character length, routing the task to both the selected entry’s `Team_Key` and its project.
2. IF two or more configured path prefixes match the task’s file path with an identical character length, THEN THE System SHALL select the first such entry by the map’s defined ordering and record a deterministic tie-break indication.
3. IF no configured path prefix matches the task’s file path, THEN THE System SHALL assign the consumer-configured default team and default project.
4. IF no configured path prefix matches the task’s file path AND no default team and default project are configured, THEN THE System SHALL leave the task’s team and project unassigned and produce an indication that no team and project could be resolved, without terminating processing of remaining tasks.
5. IF the consumer-supplied `ProjectByPath` map is empty or absent, THEN THE System SHALL apply the default-team-and-default-project resolution defined in criteria 3 and 4 to every task.
6. THE System SHALL NOT contain any hardcoded team key, project name, project identifier, or path prefix, deriving all such values from consumer-supplied configuration; framework directory names such as `.kiro/specs/`, `specs/`, `openspec/`, and `bmad/` are generic discovery defaults and not Linear routing defaults.

### Requirement 5: Matching and confidence

**User Story:** As a maintainer, I want each task matched to at most one existing issue with a clear confidence, so that re-runs are stable and ambiguous matches are flagged across frameworks.

#### Acceptance Criteria

1. WHEN scoring a task against an issue, THE System SHALL compute a score as an unbounded weighted INTEGER sum of signals using configurable weights each greater than or equal to 0 (defaults, all overridable: durable UUID match 250, awarded WHERE the issue carries a `Sync_Attachment` whose `Attachment_Metadata` holds under the `Metadata_Namespace_Key` a `Sync_State_Payload` whose task UUID equals the task’s UUID; existing Markdown issue reference 220; local-task-ID match 110; exact normalized title 100; contained normalized title 65; fuzzy title similarity contributing up to 60 points scaled by a 0.0–1.0 token-overlap ratio; same-project alignment 10; same-framework alignment 10).
2. WHEN scoring completes, THE System SHALL assign exactly one confidence band from the set {high, medium, low, unmatched} using the configurable medium-floor and plausible-match-floor thresholds (defaults, overridable: medium floor 50, plausible-match floor 18), where the medium floor is greater than or equal to the plausible-match floor; a score at or above the medium floor SHALL be high or medium, a score at or above the plausible-match floor but below the medium floor SHALL be low, and a score below the plausible-match floor SHALL be unmatched.
3. IF more than one issue has a `Sync_Attachment` whose `Attachment_Metadata` carries the same task UUID under the `Metadata_Namespace_Key`, THEN THE System SHALL abort the run, apply no changes, and report the task UUID and the identifiers of all conflicting issues.
4. WHILE selecting matches, THE System SHALL restrict usable candidates to those whose score is greater than or equal to the plausible-match threshold.
5. WHERE a candidate is not a durable-identity match AND its task’s resolved team differs from the issue’s team OR its task and issue belong to different projects OR both the task and issue carry a known `Framework_Id` and those framework identifiers differ, THE System SHALL exclude that candidate from selection.
6. WHEN assigning matches globally, THE System SHALL solve a maximum-weight one-to-one assignment so that each task maps to at most one issue and each issue maps to at most one task.
7. IF more than one maximum-weight assignment solution exists, THEN THE System SHALL select among them using a deterministic tie-break over a stable ordering of tasks and issues so that repeated runs over unchanged inputs produce byte-for-byte identical matches.
8. IF a chosen match is not a durable identity, is in the high confidence band, and its `Match_Margin` (the score difference between the chosen candidate and the next-best usable candidate) is below the configurable minimum margin (default 10, minimum allowed value 1; overridable), THEN THE System SHALL downgrade the match to the medium band and record an ambiguity reason.
9. WHERE a match is a durable identity, THE System SHALL bypass both the team gating and the project gating (criterion 5), the framework gating (criterion 5), and the margin downgrade (criterion 8), so that an issue moved or renamed across teams, projects, or frameworks is never orphaned.
10. WHEN recording a match, THE System SHALL retain up to three alternative candidates ordered by descending score, breaking ties deterministically, each annotated with its mapped or unmapped status.
11. WHEN resolving the durable UUID match signal for a task, THE System SHALL read the candidate task UUID from the `Sync_Attachment`’s `Attachment_Metadata` (obtained by querying the attachments for the task’s deterministic `Attachment_URL` or by scanning the issue’s attachments) and SHALL NOT read task identity from the issue description or from any in-file marker.

### Requirement 6: Issue-title derivation

**User Story:** As a maintainer, I want issue titles derived by configurable rules and feature prefixes, so that titles fit my conventions without hardcoded formats across frameworks.

#### Acceptance Criteria

1. WHEN deriving an issue title for a task, THE System SHALL evaluate the configured ordered title rules in ascending order and select the first rule whose conditions match the task attributes.
2. IF no configured title rule matches the task, THEN THE System SHALL fall back to the built-in default title derivation defined in criterion 7 for that task, without terminating processing of remaining tasks.
3. IF the configured ordered title rules collection is empty or absent (the built-in default is an empty rule set), THEN THE System SHALL apply the built-in default title derivation defined in criterion 7 to all tasks.
4. WHEN a consumer-supplied title rule matches, THE System SHALL apply that rule’s template, substituting each declared task attribute placeholder (including prefix, local ID, framework, feature, phase, and title) with the corresponding task attribute value.
5. IF a matched rule’s template references a placeholder for which the task provides no corresponding attribute value, THEN THE System SHALL substitute an empty string for that placeholder and produce an outcome indicator identifying the unresolved placeholder.
6. WHEN rendering a derived title back into Markdown, THE System SHALL remove every configured strip-prefix pattern, any redundant leading issue prefix, and a duplicate leading local-task-identifier prefix, preserving all other title characters unchanged.
7. WHERE the consumer supplies no title rules, THE System SHALL apply a built-in default title derivation that sets each issue title to the task’s raw title unchanged; and WHERE the consumer supplies no strip-prefix patterns, THE System SHALL apply a built-in default strip-prefix behavior that removes only the leading local-task-identifier prefix (the task’s local ID followed by a colon and a single space) and any redundant leading issue prefix, and removes no other prefix, such that neither built-in default contains any organization-specific or product-specific literal prefix.
8. WHERE a task has a `Feature_Name`, THE System SHALL, as a built-in non-configurable step applied automatically after the title derivation defined in criteria 1 through 7 completes, prepend the verbatim `Feature_Name` followed by a colon and a single space to the derived title, producing a final title of the form `<Feature_Name>: <derived-title>` (for example, a folder named `user-authentication` yields the prefix `user-authentication: `), independent of any consumer title rule.
9. THE System SHALL apply the `Feature_Name` prefix defined in criterion 8 to the derived title regardless of whether a consumer title rule matched, no consumer title rule matched, or the built-in pass-through default of criterion 7 produced the title, decorating the already-derived title in every case.
10. IF the derived title already begins with the exact prefix formed by the `Feature_Name` followed by a colon and a single space, THEN THE System SHALL retain the title unchanged and SHALL NOT prepend a second occurrence of that prefix, so that repeated derivations over unchanged inputs produce a byte-for-byte identical final title.
11. WHERE a task has no `Feature_Name`, THE System SHALL produce the final title as the derived title of criteria 1 through 7 unchanged and SHALL add no feature prefix.
12. WHEN rendering a derived title back into Markdown, THE System SHALL remove a leading prefix formed by the `Feature_Name` followed by a colon and a single space, in addition to removing every configured strip-prefix pattern, redundant issue prefix, and duplicate local ID as defined in criterion 6, such that a subsequent parse then derivation reproduces the same final title and titles are not progressively prefixed across runs.
13. WHEN a task’s final derived title is submitted for propagation, THE System SHALL apply the `Security_Screener` title check defined in Requirement 10 to the final `Feature_Name`-prefixed title, such that the screened value is the fully prefixed title rather than the pre-prefix derived title.

> **Informative note (non-normative; not a requirement):** A consumer MAY optionally supply an ordered title-rule preset that reproduces a common convention. Expressed with neutral placeholders, such a preset could include, in order:
> - a rule matching tasks under an infrastructure area that have a local ID → template `{areaPrefixA} {localId}: {title}`;
> - a rule matching tasks under a delivery/pipeline area that have a phase → template `{areaPrefixB} Phase {phase}: {title}`, and the same area without a phase → template `{areaPrefixB}: {title}`;
> - a rule matching a checklist child task → raw template `{title}`;
> - a catch-all rule → template `{areaPrefixC}: {title}`;
>
> with corresponding strip-prefixes for `{areaPrefixA}`, `{areaPrefixB}` (optionally followed by `Phase <n>`), and `{areaPrefixC}`, plus the leading local-ID prefix. The area prefixes and area definitions shown here are illustrative placeholders supplied entirely by the consumer; they are NOT built-in defaults, and the tool ships none of them.

### Requirement 7: Framework adapters for BMAD, GitHub SpecKit, open-spec, and Kiro

**User Story:** As a maintainer using multiple spec-driven development frameworks, I want built-in adapters that understand each framework’s task storage and task-identifier conventions, so that `task-linear-sync` can discover, parse, render, and reconcile tasks without framework-specific forks.

#### Acceptance Criteria

1. THE System SHALL provide built-in `Framework_Adapter`s for `bmad`, `spec-kit`, `open-spec`, `kiro`, and `generic`.
2. WHEN framework selection is `auto`, THE System SHALL infer `Framework_Id` from the task file path and optional sibling-document markers using deterministic precedence, including: `kiro` WHERE the path is beneath `.kiro/`; `open-spec` WHERE the path contains `openspec/` or `open-spec/` or sibling markers such as `openspec.json` or `proposal.md`; `spec-kit` WHERE the path is beneath `specs/` or `spec/` and sibling markers such as `spec.md` or `plan.md` are present; `bmad` WHERE the path contains `bmad/`, `bmad-method/`, or sibling markers such as `prd.md` or `architecture.md`; otherwise `generic`.
3. IF multiple adapters match a task file, THEN THE System SHALL select one using the longest matching configured path or base-directory pattern, then the configured adapter precedence, then deterministic alphabetical tie-break, and SHALL record the selected `Framework_Id`.
4. THE active `Framework_Adapter` SHALL supply, directly or via configuration, task-file patterns, base directories, framework detection rules, `Feature_Name` extraction rules, heading/checklist identifier grammar, phase/summary/rollup patterns, sibling document names, default title strip prefixes, and optional agent-hook template behavior.
5. THE System SHALL provide built-in adapter defaults including:
   - `kiro`: base directory `.kiro/specs/`, task file `tasks.md`, `Feature_Name` as the immediate parent directory beneath `.kiro/specs/`, sibling documents `requirements.md` and `design.md`, and agent-hook directory `.kiro/hooks/`;
   - `spec-kit`: base directories `specs/` and `spec/`, task file `tasks.md`, `Feature_Name` as the immediate feature directory beneath a base directory, sibling documents `spec.md`, `plan.md`, and `requirements.md`;
   - `open-spec`: base directories `openspec/` and `open-spec/`, task file `tasks.md`, `Feature_Name` as the meaningful segment after `openspec/`, `changes/`, or `specs/` where present, sibling documents `spec.md`, `proposal.md`, and `tasks.md`;
   - `bmad`: base directories `bmad/`, `bmad-method/`, and `docs/`, task file `tasks.md`, `Feature_Name` as the immediate parent directory or task-file basename when no parent feature directory is present, sibling documents `requirements.md`, `design.md`, `architecture.md`, `prd.md`, and `spec.md`;
   - `generic`: task file `tasks.md`, base directories from the configured `Specs_Base_Directories`, `Feature_Name` from the immediate parent directory beneath a configured base when present, and broad task-identifier grammar.
6. THE System SHALL allow consumers to override framework selection, adapter precedence, task-file patterns, base directories, heading grammar, phase/summary/rollup patterns, sibling document names, `Feature_Name` extraction behavior, and title strip prefixes, and SHALL allow custom framework adapter configuration that supplies at least an adapter id, path/base-directory patterns, and heading grammar.
7. THE System SHALL record `Framework_Id` and `Framework_Metadata` on every discovered task and SHALL persist them in the `Sync_State_Payload`.
8. THE System SHALL NOT hardcode organization-specific paths, team keys, project identifiers, workflow state identifiers, or tokens in framework adapters; framework directory names such as `.kiro/specs/`, `specs/`, `openspec/`, and `bmad/` are generic discovery defaults and are overridable.
9. WHERE the selected framework is `generic`, THE System SHALL use the broad built-in heading/checklist grammar and SHALL apply no framework-specific exclusions beyond the global summary and rollup defaults.
10. THE System SHALL preserve Kiro compatibility by continuing to discover `.kiro/specs/*/tasks.md`, derive `Feature_Name` from the Kiro feature directory, and support `.kiro/hooks/` agent-hook scaffolding when the `kiro` adapter is selected.

### Requirement 8: Linear integration via a port

**User Story:** As an integrator, I want all Linear access behind a single injectable port with safe retries, so that I can test with a fake and rely on resilient, non-duplicating calls.

#### Acceptance Criteria

1. THE System SHALL route all Linear GraphQL access through the `Linear_Port` interface, such that no component issues Linear GraphQL requests except through an injected implementation of `Linear_Port`.
2. WHEN listing issues, THE System SHALL paginate results in batches not exceeding the configured page size (default 100, range 1 to 250 items per page; overridable) and SHALL retrieve all pages until no further page is available.
3. WHEN listing issues, THE System SHALL batch across all configured teams and include only issues that belong to at least one of the configured teams AND that belong to at least one of that team’s configured project IDs AND that are not in any state whose type appears in the configured ignored state types (default `["canceled","duplicate"]`; overridable), preserving per-team scoping so that an issue is included only when it satisfies the team, project, and state constraints of one of the configured teams.
4. WHEN discovering metadata, THE System SHALL batch across all configured teams and fetch, for each configured team, the team key, the list of projects, and the list of workflow states, and SHALL return each of the three collections per configured team.
5. THE System SHALL provide operations to get an issue by ID, find issues by embedded task UUID, create an issue, update an issue, and archive an issue, WHERE finding issues by embedded task UUID is performed by querying the attachments for the task’s deterministic `Attachment_URL` or by scanning an issue’s attachments and reading the task UUID from the `Sync_Attachment`’s `Attachment_Metadata`, and not by searching issue descriptions.
6. THE System SHALL provide attachment operations to create-or-update a `Sync_Attachment` addressed by its `Attachment_URL`, update a `Sync_Attachment`, query the attachments for a given URL, and list an issue’s attachments.
7. WHEN creating a `Sync_Attachment` whose `Attachment_URL` already exists on the same issue, THE System SHALL rely on the issue-tracker’s URL idempotency so that the existing attachment is updated in place rather than duplicated, such that the System need not store the attachment identifier to perform a subsequent update.
8. WHEN listing an issue’s attachments, THE System SHALL paginate using cursor-based pagination, requesting successive pages by passing the previous page’s end cursor and continuing until the page information reports no further page is available.
9. THE System SHALL NOT automatically retry issue creation, such that a failed issue creation results in exactly one submitted create request.
10. IF a Linear request other than issue creation fails with an HTTP 429 status, a 5xx status, or a network error, THEN THE System SHALL retry that request using exponential backoff with randomized jitter, up to the configured maximum number of retries (default 5, range 0 to 10 additional attempts; overridable).
11. WHILE retrying a request that returned a `Retry-After` header, THE System SHALL wait at least the duration indicated by that header before the next attempt.
12. IF a Linear request fails after exhausting the configured maximum retries or fails with a non-retryable error, THEN THE System SHALL raise a diagnostic that names the GraphQL operation, omits credential values, and does not exceed 2000 characters, and SHALL not perform further retries for that request.
13. WHERE an access token does not begin with the configured personal-key prefix (default `lin_api_`; overridable), THE System SHALL set the `Authorization` header using the `Bearer` scheme; otherwise THE System SHALL set the `Authorization` header to the personal key as a raw value.
14. THE System SHALL read credentials from configurable environment-variable names (defaults: access token from `LINEAR_ACCESS_TOKEN` applied with the `Bearer` scheme, API key from `LINEAR_API_KEY` applied as a raw value; both overridable), and IF a required credential environment variable is unset or empty, THEN THE System SHALL reject the operation before issuing any request and raise a diagnostic identifying the missing credential by variable name without disclosing its value.
15. WHEN operating across the set of configured teams for metadata discovery and issue listing, THE System SHALL complete the multi-team routing matrix within a single workspace by retrieving across the configured teams rather than requiring fully separate sequential passes where the transport permits combined retrieval, while preserving per-team scoping and the pagination, retry-with-backoff, `Retry-After`, credential, and diagnostic behavior defined in criteria 2 and 8 through 14.
16. THE System SHALL provide attachment operations to create-or-update, update, and query a `Continuation_Attachment` addressed by its deterministic `Continuation_Attachment_URL` and to enumerate a task’s attachment chain by walking pages from the page-0 canonical `Attachment_URL` upward, incrementing the page index until no further `Continuation_Attachment` is found, WHERE finding issues by embedded task UUID and durable-identity matching continue to key solely off the page-0 canonical `Attachment_URL` per criterion 5 and Requirement 5, and `Continuation_Attachment`s serve only to hold later pages of the append-only `Sync_History_Log` and are never used for durable-identity matching.

### Requirement 9: Sync modes and configurable conflict resolution

**User Story:** As a maintainer, I want bootstrap and sync modes with configurable, git-like conflict-resolution actions per conflict type, so that first runs seed Linear and later runs reconcile managed-description changes according to rules I control.

#### Acceptance Criteria

1. WHEN a plan or worker operation begins and no checkpoint exists for the repository, THE System SHALL select `Bootstrap_Mode`.
2. WHEN a plan or worker operation begins and a checkpoint exists for the repository, THE System SHALL select `Sync_Mode`.
3. WHILE in `Sync_Mode`, WHEN evaluating a matched task’s Linear issue description against the task’s `Task_Body`, THE System SHALL classify the `Description_Conflict_Type` as `linear-changed` IF the Linear issue description changed since the checkpoint by a `Meaningful_Diff` per criterion 21 and the `Task_Body` did not, as `spec-changed` IF the `Task_Body` changed since the checkpoint by a `Meaningful_Diff` per criterion 21 and the Linear issue description did not, and as `both-changed` IF both the `Task_Body` and the Linear issue description changed since the checkpoint each by a `Meaningful_Diff` per criterion 21.
4. WHILE in `Bootstrap_Mode`, WHERE no checkpoint exists, WHEN evaluating a matched task’s Linear issue description and the task’s `Task_Body` differs from the Linear issue description by a `Meaningful_Diff` per criterion 21 (a difference persisting after normalization), THE System SHALL classify the `Description_Conflict_Type` as `both-changed`, and WHERE the `Task_Body` equals the Linear issue description after normalization per criterion 21, THE System SHALL make no description change and record no conflict.
5. WHEN a `Description_Conflict_Type` has been classified for a matched task, THE System SHALL look up the `Conflict_Action` mapped to that `Description_Conflict_Type` in the active mode’s configured conflict-action map (the `Bootstrap_Mode` map while in `Bootstrap_Mode`, the `Sync_Mode` map while in `Sync_Mode`) and apply that `Conflict_Action`.
6. IF the resolved `Conflict_Action` is `overwrite-linear`, THEN THE System SHALL push the task’s `Task_Body` to Linear, overwriting the whole Linear issue description, and record a reason identifying the `Description_Conflict_Type` and the `overwrite-linear` action.
7. IF the resolved `Conflict_Action` is `overwrite-spec`, THEN THE System SHALL write Linear’s current description into the task’s `Task_Body` region in the local spec file using `Conflict_Markers`, embedding the current local `Task_Body` content between the `<<<<<<< spec (local)` start line and the `=======` separator and Linear’s current description content between the `=======` separator and the `>>>>>>> linear (remote)` end line, SHALL leave the Linear description unchanged, SHALL NOT push the `Task_Body` to Linear, and SHALL record a reason identifying the `Description_Conflict_Type` and the `overwrite-spec` action.
8. IF the resolved `Conflict_Action` is `report-only`, THEN THE System SHALL make no change to either the task’s `Task_Body` or the Linear issue description and SHALL record the conflict in the plan and report with its `Description_Conflict_Type` and the `report-only` action.
9. IF the resolved `Conflict_Action` is `skip`, THEN THE System SHALL make no change to either the task’s `Task_Body` or the Linear issue description and SHALL NOT surface the item as a conflict needing attention, recording it internally only.
10. IF the resolved `Conflict_Action` is `prefer-newer`, THEN THE System SHALL compare the checkpoint’s recorded Linear updated-at timestamp against the `Task_Body` change indication and SHALL apply the `overwrite-linear` effect defined in criterion 6 WHERE the `Task_Body` (spec) side is more recent and the `overwrite-spec` `Conflict_Markers` effect defined in criterion 7 WHERE the Linear side is more recent; IF the relative recency cannot be determined, THEN THE System SHALL fall back to the `report-only` effect defined in criterion 8.
11. IF the resolved `Conflict_Action` is `fail`, THEN THE System SHALL abort the run before performing any further mutation and SHALL report the `Description_Conflict_Type` and the `fail` action so that a human can resolve the conflict.
12. THE System SHALL provide built-in default conflict-action maps, each overridable per entry, of: for `Bootstrap_Mode`, `linear-changed` = `overwrite-linear`, `spec-changed` = `overwrite-linear`, and `both-changed` = `overwrite-linear`; for `Sync_Mode`, `spec-changed` = `overwrite-linear`, `linear-changed` = `overwrite-spec`, and `both-changed` = `report-only`.
13. WHEN a checklist task’s checked state changed in the repository since the checkpoint and the corresponding issue is unchanged since the checkpoint, IF the task is checked, THEN THE System SHALL set the desired issue state to the configured done state, independently of the managed-description `Conflict_Action`.
14. WHEN a checklist task’s checked state changed in the repository since the checkpoint and the corresponding issue is unchanged since the checkpoint, IF the task is unchecked, THEN THE System SHALL set the desired issue state to the configured backlog state, independently of the managed-description `Conflict_Action`.
15. WHEN evaluating a matched task whose `Task_Body` region in the spec file contains `Conflict_Markers` (an `Unresolved_Conflict_Block`), THE System SHALL treat the region as an unresolved conflict, SHALL make no change to that task’s Linear issue description or its spec `Task_Body` region, SHALL NOT push the `Task_Body` to Linear, SHALL NOT write additional or nested `Conflict_Markers`, and SHALL report the task as an unresolved conflict, until the `Conflict_Markers` are removed and the `Task_Body` region is clean.
16. THE System SHALL apply the `Description_Conflict_Type` classification and the conflict-action map defined in criteria 3 through 15 solely to the whole tool-managed Linear issue description (which mirrors the task’s `Task_Body`), and SHALL NOT apply that conflict machinery to the `Sync_State_Payload` carried in the `Sync_Attachment`’s `Attachment_Metadata`.
17. WHEN applying to a matched task, THE System SHALL write the non-history `Sync_State_Payload` state (the durable identity anchor, `Framework_Metadata`, the managed-description content hash, and sync cursors or timestamps) into the page-0 canonical `Sync_Attachment`’s `Attachment_Metadata` as tool-owned state, upserting that page-0 `Sync_Attachment` by its `Attachment_URL` and authoritatively rewriting the non-history payload each apply after screening per Requirement 10, independently of the resolved managed-description `Conflict_Action`, AND SHALL upsert the append-only `Sync_History_Log` into the current (highest-page) `Sync_Attachment` of the task’s attachment chain per criteria 18 and 19.
18. WHEN applying a sync action that affects a matched task (including creating the issue, matching the task to an issue, updating the title, updating the managed description, changing the checkbox or workflow state, detecting a conflict, or rolling back the run), THE System SHALL append exactly one screened `Sync_History_Event` describing that action, with a human-readable timestamp, to the end of the task’s append-only `Sync_History_Log`, and SHALL NOT modify or delete any previously-appended `Sync_History_Event`, WHERE the reverting of a run is recorded by appending a `Sync_History_Event` of the `rollback` event kind that references the sync action or actions it reverses rather than by removing or rewinding any earlier entry.
19. WHILE appending a `Sync_History_Event`, IF appending it to the current (highest-page) `Sync_Attachment` of the task’s attachment chain would exceed the configured per-page rollover threshold (`History_Log_Max_Entries`) or the practical attachment metadata size limit, THEN THE System SHALL create the next deterministic paged `Continuation_Attachment` (incrementing the page index) addressed by its `Continuation_Attachment_URL` and append the new `Sync_History_Event` to that new page, WITHOUT modifying or deleting any prior page or any previously-appended `Sync_History_Event`, so that the complete append-only history is preserved across the attachment chain.
20. WHEN appending a `Sync_History_Event` to the `Sync_History_Log`, THE System SHALL apply the `Security_Screener` to the event’s human-readable description per Requirement 10 before the event is appended to the current page.
21. WHEN comparing a matched task’s Linear issue description against the task’s `Task_Body` for the `Sync_Mode` classification of criterion 3, for the `Bootstrap_Mode` comparison of criterion 4, or for any change detection against the checkpoint, THE System SHALL compare a normalized form of each side produced by applying the same configurable `Description_Normalization_Profile` to both sides rather than comparing the raw bytes, SHALL treat as a `Meaningful_Diff` only a difference that persists after both sides are so normalized, and SHALL treat a difference that does not persist after normalization as insignificant, classifying it as no `Description_Conflict_Type`, triggering no `Conflict_Action`, and causing no Linear description write and no `Conflict_Markers` write, WHERE the `Description_Normalization_Profile` removes insignificant formatting differences before comparison including but not limited to trailing whitespace on lines, leading and trailing blank lines, differences in line-ending style (for example CRLF versus LF), collapsing of consecutive blank-line runs, and other round-trip Markdown formatting the issue tracker may introduce, and WHERE the `Description_Normalization_Profile` has a sensible built-in default and is overridable per Requirement 17.
22. WHERE comparing a matched task’s Linear issue description against the task’s `Task_Body` per criterion 21 yields no `Meaningful_Diff` (only insignificant formatting differences), THE System SHALL treat the Linear issue description and the `Task_Body` as equal, SHALL make no description mutation, and SHALL record no conflict, so that repeated syncs over unchanged inputs neither oscillate nor repeatedly rewrite the description.

### Requirement 10: Security screening

**User Story:** As a security-conscious maintainer, I want secrets and PII redacted before propagation and logging, so that sensitive data never reaches Linear, reports, or logs.

#### Acceptance Criteria

1. WHEN screening text, THE System SHALL redact each occurrence of a blocking secret or PII category, including private keys, authorization tokens, JWTs, provider API tokens, credential assignments, and personal identifiers, replacing the matched value with a fixed redaction placeholder and recording a finding with a category label and a blocked status.
2. WHEN screening text that contains one or more email addresses, THE System SHALL replace each email address with a fixed redaction placeholder and record one non-blocking finding per distinct email address.
3. WHEN screening text that contains a term from the configurable review-only terminology list, THE System SHALL record one non-blocking finding per matched term without altering the term in the output.
4. WHEN serializing any report, manifest, or log value, THE System SHALL traverse the value to unlimited nesting depth, apply the blocking and non-blocking redaction rules of criteria 1 through 3 to every string, and replace the value of any object key whose name matches the configurable secret-key-name list with a fixed redaction placeholder regardless of the value content.
5. IF a task-derived Linear title fails screening, where failure is defined as the screened output differing from the input text or at least one blocked finding being produced, THEN THE System SHALL abort the run before propagating the title, retain the original input without transmitting it, and report the count and category labels of each contributing finding.
6. WHEN a `Sync_Attachment` is submitted for propagation, THE System SHALL apply the blocking and non-blocking redaction rules of criteria 1 through 4 to the `Sync_State_Payload` and every string value within the `Attachment_Metadata`, and to the attachment’s title and subtitle, before transmitting the attachment to Linear.
7. IF the `Sync_State_Payload`, the `Attachment_Metadata`, the attachment title, or the attachment subtitle produces at least one blocked finding during screening, THEN THE System SHALL abort the run before propagating the `Sync_Attachment`, transmit none of the affected values, and report the count and category labels of each contributing finding.
8. WHEN screening the `Sync_State_Payload` for propagation, THE System SHALL apply the blocking and non-blocking redaction rules of criteria 1 through 4 to the human-readable description and every string value of each `Sync_History_Event` within the `Sync_History_Log`, such that every history event is screened before it is written into the `Attachment_Metadata`.
9. WHEN the `Sync_History_Server` renders any `Sync_History_Event` value that could contain sensitive content into a response destined for the browser, THE System SHALL re-apply the blocking and non-blocking redaction rules of criteria 1 through 4 to that value before transmitting the response to the client.
10. WHEN an issue description (the task’s `Task_Body`) is submitted for propagation to Linear, THE System SHALL apply the blocking and non-blocking redaction rules of criteria 1 through 4 to that description content before transmitting it, and IF the description content produces at least one blocked finding during screening, THEN THE System SHALL abort the run before propagating the description, transmit none of the affected content, and report the count and category labels of each contributing finding.

### Requirement 11: State, encryption, and locking

**User Story:** As a maintainer, I want run state stored securely outside my repository, so that no secrets are committed and runs are recoverable and mutually exclusive.

#### Acceptance Criteria

1. THE System SHALL store all run state outside the repository working tree, in a consumer-configured directory when one is provided, or otherwise (default, overridable) in a per-repository directory under the platform’s application-support/state location whose name is keyed by a hash of the canonical absolute repository root path.
2. WHEN creating a state directory, THE System SHALL set its permissions so that only the owner has read, write, and execute access, and no access is granted to group or other principals.
3. WHEN creating a state file, THE System SHALL set its permissions so that only the owner has read and write access, and no access is granted to group or other principals.
4. WHEN writing any state file, THE System SHALL write the content to a temporary file, set owner-only permissions on it, then atomically rename it over the target path, such that a concurrent reader observes either the complete prior content or the complete new content and never a partial write.
5. THE System SHALL provide a configurable audit-manifest-enabled flag (default `true`), and WHERE the audit manifest is disabled, THE System SHALL write no `Audit_Manifest` and SHALL perform no run journaling to a manifest, such that the resumable rollback capability is unavailable per Requirement 12 and the `rollback` command refuses per Requirement 15.
6. THE System SHALL provide a configurable audit-manifest-encryption-enabled flag (default `true`) that applies only WHERE the audit manifest is enabled, because when no manifest is written there is nothing to encrypt.
7. WHERE the audit manifest is enabled AND audit-manifest encryption is enabled, WHEN persisting an audit manifest, THE System SHALL encrypt the manifest contents using AES-256-GCM and store the result in a versioned envelope containing a schema version identifier, the key identifier, the initialization vector, the authentication tag, and the ciphertext.
8. WHERE the audit manifest is enabled AND audit-manifest encryption is disabled, WHEN persisting an audit manifest, THE System SHALL persist the manifest contents unencrypted and without an encryption envelope, still writing atomically with owner-only permissions per criteria 3 and 4.
9. WHERE the audit manifest is enabled AND audit-manifest encryption is enabled, THE System SHALL obtain the encryption key from a consumer-configured environment variable or a pluggable platform key store, and SHALL NOT store the key within, alongside, or in the same file as the ciphertext.
10. WHERE the audit manifest is enabled AND audit-manifest encryption is enabled, IF the encryption key cannot be obtained from the configured source when encryption or decryption is required, THEN THE System SHALL abort the operation without writing or reading the affected manifest and SHALL return an error indicating the key is unavailable.
11. WHERE the audit manifest is enabled AND audit-manifest encryption is enabled, IF a manifest fails AES-256-GCM authentication tag verification during decryption, THEN THE System SHALL reject the manifest, SHALL NOT return its plaintext contents, and SHALL return an error indicating the manifest is invalid or tampered.
12. WHERE the audit manifest is enabled AND audit-manifest encryption is disabled, WHEN loading a manifest, THE System SHALL read the plaintext manifest contents directly without requiring an encryption key and without performing authentication-tag verification.
13. WHERE the audit manifest is enabled, WHEN loading a manifest, THE System SHALL treat the manifest as expired if the elapsed time since its recorded creation timestamp exceeds the configured expiry duration (default 30 days; overridable), and SHALL treat it as valid otherwise, applying this expiry behavior regardless of whether audit-manifest encryption is enabled or disabled.
14. WHEN attempting a mutating run, THE System SHALL acquire an advisory lock that records the acquiring process identifier and an acquisition timestamp, and SHALL NOT proceed if a valid lock held by a live process already exists.
15. WHEN attempting a mutating run and an existing lock is present, THE System SHALL take over the lock only if the recorded process is no longer alive and the elapsed time since the lock’s recorded timestamp exceeds the configured stale-takeover threshold (default 60 seconds; overridable).
16. WHEN a create attempt begins, THE System SHALL persist a `Create_Intent` record capturing its current lifecycle status before performing the mutating operation.
17. WHEN a run produces a report, THE System SHALL write a sanitized JSON report and a sanitized Markdown report containing no secret or key material, and SHALL update the last-run marker to reference the completed run.

### Requirement 12: Plan, apply, and rollback engine

**User Story:** As a maintainer, I want a read-only plan, a journaled apply, and a resumable rollback, so that changes are reviewable, safe, and reversible.

#### Acceptance Criteria

1. WHEN building a plan, THE System SHALL perform zero issue-tracker mutations and zero repository file writes, and SHALL restrict all activity to read and in-memory operations.
2. WHEN building a plan, THE System SHALL record a content hash for each scanned input file and the current version-control HEAD commit identifier, and SHALL persist these values as stability guards for later comparison.
3. IF any recorded input file content hash differs from its plan-time value, or if the version-control HEAD commit identifier differs from its plan-time value, evaluated at apply start, THEN THE System SHALL abort before performing any mutation and SHALL report an error indicating that inputs changed since plan build, with no mutation performed.
4. WHEN applying a plan, THE System SHALL re-fetch each matched issue immediately before mutating it, and IF the re-fetched snapshot differs from the planned snapshot in any compared field, THEN THE System SHALL abort before mutating that issue and SHALL report an error indicating a snapshot mismatch.
5. WHEN applying a plan, THE System SHALL create issues in an order where every parent issue is created before any of its child issues, and SHALL emit sibling issues within the same parent in the reverse of their working order.
6. WHERE the audit manifest is enabled, WHEN applying a plan, THE System SHALL write a running manifest containing the backup of each file to be modified, the checkpoint-before snapshot, and one audit record per planned operation, and SHALL complete this write before performing the first mutation; WHERE the audit manifest is disabled, THE System SHALL write no running manifest and SHALL perform no run journaling, and SHALL still proceed with the mutating apply without a resumable-rollback safety net.
7. IF an issue-creation attempt returns an error and reconciliation finds a count of Linear issues carrying a `Sync_Attachment` whose `Attachment_Metadata` holds the task’s UUID not equal to exactly 1 (that is, 0 or 2 or more), THEN THE System SHALL record the create as indeterminate, SHALL abort further creation for that task, and SHALL NOT automatically retry the create.
8. WHERE the audit manifest is enabled AND an audit manifest exists for the target run, WHEN rolling back a run, THE System SHALL restore each backed-up file to its checkpoint-before content, restore each updated issue field to its checkpoint-before value, archive each issue created during the run, and either restore or remove the checkpoint to match its checkpoint-before state; WHERE audit manifests are disabled OR no audit manifest is available for the target run, THE System SHALL make the rollback operation unavailable, perform no changes, and report that rollback cannot be performed because no audit manifest is available.
9. WHERE the audit manifest is enabled AND an audit manifest exists for the target run, WHILE rolling back a run, THE System SHALL guard each rollback step so that a rollback interrupted after partial completion can be resumed without repeating already-completed steps, and IF the current state of any guarded step matches neither its before state nor its result state, THEN THE System SHALL report a conflict for that step and SHALL halt further rollback of that step.
10. WHEN building a plan, THE System SHALL include each planned `Sync_Attachment` create-or-update (page-0 canonical and any `Continuation_Attachment`) as a planned operation, and WHERE the audit manifest is enabled, WHEN applying a plan, THE System SHALL journal each such attachment create-or-update as an audit record within the running manifest defined in criterion 6, capturing the target issue, the `Attachment_URL` or `Continuation_Attachment_URL`, and the checkpoint-before `Attachment_Metadata` WHERE a prior `Sync_Attachment` existed; WHERE the journaled record concerns the append-only `Sync_History_Log`, the recorded rollback action is to append a `rollback` `Sync_History_Event` per criterion 12 rather than to restore prior `Attachment_Metadata`.
11. WHEN applying a `Sync_Attachment` upsert to the page-0 canonical `Attachment_URL` or to a `Continuation_Attachment_URL`, THE System SHALL rely on the URL idempotency defined in Requirement 8 so that re-running an interrupted or repeated apply over unchanged inputs updates the same attachment in place and produces no duplicate attachment on any page.
12. WHERE the audit manifest is enabled AND an audit manifest exists for the target run, WHEN rolling back a run, THE System SHALL treat the append-only `Sync_History_Log` as never rewound: THE System SHALL NOT restore any `Sync_Attachment`’s `Attachment_Metadata` to a prior history state, SHALL NOT delete, archive, or remove any `Continuation_Attachment` created for history during the run, SHALL NOT remove any previously-appended `Sync_History_Event`, and SHALL retain any page-0 canonical `Sync_Attachment` created during the run so that the durable identity anchor and history are preserved (superseding, for the `Sync_Attachment` specifically, the archive-or-remove-created-attachment behavior that criterion 8 applies to issues); instead THE System SHALL append one screened `rollback` `Sync_History_Event` per Requirement 9, criterion 18, recording that the run was reverted and referencing the reversed sync action or actions, WHILE the create-then-archive rollback of issues (criterion 8), the file and issue-field restoration (criteria 8 and 9), and the resumable guarding (criterion 9) remain in effect, and THE System MAY update the non-history managed sync state (content hashes and cursors that mirror the restored issue state) on the page-0 canonical `Sync_Attachment` to reflect the restored state without rewinding the history log.

### Requirement 13: Queue and background worker

**User Story:** As a developer, I want reconciliation to run in the background after git events, so that syncing does not block my workflow and transient failures recover.

#### Acceptance Criteria

1. WHEN a job is enqueued and no pending job exists, THE System SHALL write a single pending job within 500 milliseconds.
2. WHEN a job is enqueued and a pending job already exists, THE System SHALL merge the new job into the existing pending job so that at most one pending job is retained.
3. WHEN a job is enqueued, THE System SHALL spawn a detached worker within 500 milliseconds of the enqueue completing.
4. WHEN a job is enqueued, THE System SHALL schedule a delayed fallback worker to start after the configurable worker-delay interval, where the interval is an integer between 1 and 3600 seconds inclusive and defaults to 75 seconds when unset or outside this range.
5. WHEN draining the queue, THE System SHALL acquire the queue lock before reading or modifying the pending job.
6. IF the queue lock cannot be acquired within the configurable lock-acquisition timeout (an integer between 1 and 300 seconds inclusive, defaulting to 30 seconds when unset or outside this range), THEN THE System SHALL terminate the drain attempt without modifying the pending job and record a sanitized report indicating lock acquisition failure.
7. WHILE holding the queue lock, THE System SHALL reclaim any claim whose claim age exceeds the configurable abandoned-claim threshold (an integer between 1 and 3600 seconds inclusive, defaulting to 300 seconds when unset or outside this range) before claiming the pending job.
8. WHILE holding the queue lock, THE System SHALL claim the pending job atomically such that no more than one worker can hold the claim at any time.
9. WHEN a pending job has been claimed, THE System SHALL apply the job in the mode specified by the claimed job.
10. IF applying a queued job fails, THEN THE System SHALL rewrite the pending job for retry, increment the job retry count, and record a sanitized report identifying the failure cause while retaining the pending job for subsequent drains.
11. IF applying a queued job fails and the job retry count has reached the configurable maximum retry count (an integer between 1 and 100 inclusive, defaulting to 5 when unset or outside this range), THEN THE System SHALL stop rewriting the pending job for retry and record a sanitized report indicating the retry limit was reached.
12. WHEN a queued run completes, THE System SHALL update a durable last-run marker with the run outcome and completion timestamp.
13. WHILE the process is attached to a terminal, WHEN a queued run completes, THE System SHALL write the run outcome to standard error.
14. WHEN a queued run completes, THE System SHALL attempt a best-effort platform notification and SHALL continue without error if the notification cannot be delivered.
15. WHERE the configurable notification-suppression setting is enabled, THE System SHALL suppress the best-effort platform notification while still updating the durable last-run marker.

### Requirement 20: Sync-history URL routing and path parsing

**User Story:** As a Linear user who clicks a Sync_Attachment link, I want its URL to resolve to a real sync-history page for the associated task, so that I can view that task’s sync history at the same address the sync engine records in Linear.

3. 4. WHEN the request path matches the configured `Attachment_URL` template and yields a well-formed task UUID, THE `Sync_History_Server` SHALL treat the extracted task UUID as the identity anchor for resolving the sync history per Requirement 21.
5. THE `Sync_History_Server` SHALL derive its served base host, `toolId` segment, and route template solely from the configured `Attachment_URL` base host, `toolId`, and template values, and SHALL NOT hardcode any real host, `toolId`, or UUID value.

### Requirement 21: Live history read from Linear attachment metadata

**User Story:** As a viewer, I want the sync-history page to show the current history read live from Linear, so that I see up-to-date events without the web app maintaining its own primary datastore.

#### Acceptance Criteria

1. WHEN resolving sync history for an extracted task UUID, THE `Sync_History_Server` SHALL reconstruct the complete append-only history by reading the `Sync_State_Payload` from the page-0 canonical `Sync_Attachment`’s `Attachment_Metadata` via the Linear API (locating that attachment either by querying the attachments for the task’s deterministic page-0 `Attachment_URL` or by scanning an issue’s attachments, per Requirement 8) and then walking the deterministic paged `Continuation_Attachment`s by incrementing the page index in the `Continuation_Attachment_URL` template until no further `Continuation_Attachment` is found.
2. WHEN the per-page `Sync_State_Payload`s have been read across the attachment chain, THE `Sync_History_Server` SHALL deserialize the `Sync_History_Log` from the single string value stored under the `Metadata_Namespace_Key` of each page, concatenate the pages in ascending page order into the complete chronological history, present its `Sync_History_Event` entries in chronological order each with a human-readable timestamp and a human-readable description, and render a `rollback`-kind `Sync_History_Event` like any other event kind.
3. IF no page-0 canonical `Sync_Attachment` carrying the extracted task UUID is found, THEN THE `Sync_History_Server` SHALL respond with a not-found status and SHALL return no history data.
4. THE `Sync_History_Server` SHALL NOT read the encrypted local audit manifest, the `State_Directory`, or the `Checkpoint`, and SHALL NOT require the manifest encryption key to render a sync-history page.
5. THE `Sync_History_Server` SHALL NOT maintain a separate primary datastore as the source of truth for sync history, reading history live per request from the Linear `Sync_Attachment` metadata, and MAY use only an optional, non-authoritative cache per Requirement 22.
6. IF the Linear read fails after exhausting the configured retry behavior of Requirement 8, THEN THE `Sync_History_Server` SHALL respond with an error status that names no credential value and reveals no history data.

### Requirement 22: Tiered realtime transport, caching, and rate-limit respect

**User Story:** As a viewer on any hosting environment, I want near-realtime history updates that degrade gracefully, so that the page stays current on serverless, edge, containerized, and traditional Node hosts without requiring persistent connections.

#### Acceptance Criteria

1. THE `Sync_History_Server` SHALL deliver near-realtime updates to the browser using a tiered `Realtime_Transport` that prefers Server-Sent Events where the hosting environment supports long-lived responses and falls back to periodic HTTP polling where it does not.
2. THE `Sync_History_Server` SHALL always make periodic HTTP polling available as a fallback transport and SHALL NOT mandate any transport that requires a persistent stateful connection as the only option.
3. WHILE delivering realtime updates, THE `Sync_History_Server` SHALL obtain updated history server-side by re-reading the reconstructed multi-page history from the Linear `Sync_Attachment` chain (the page-0 canonical `Sync_Attachment` and its `Continuation_Attachment`s per Requirement 21) on the configured poll/refresh interval (default 15 seconds; range 1–3600 seconds; overridable).
4. WHERE server-side caching is enabled, THE `Sync_History_Server` SHALL serve the cached reconstructed multi-page history for a given task UUID until the configured cache TTL (default 10 seconds; range 0–3600 seconds where 0 disables caching; overridable) elapses, after which THE `Sync_History_Server` SHALL re-read the attachment chain from Linear.
5. THE `Sync_History_Server` SHALL treat any server-side cache as optional and pluggable and SHALL NOT require a cache, a filesystem write, a specific database, or long-lived in-process state for correct rendering of a sync-history page.
6. WHILE reading history from Linear, THE `Sync_History_Server` SHALL respect Linear rate limits by applying the exponential-backoff-with-jitter and `Retry-After` behavior defined in Requirement 8.
7. THE `Sync_History_Server` SHALL run on serverless function, edge, containerized Node, and traditional Node hosting environments without requiring a mandatory filesystem write, a mandatory database, or mandatory long-lived in-process state.

THE System SHALL provide a middle layer of integration tests exercising component interactions through an injected fake `Linear_Port` per Requirement 8, including the plan, apply, and rollback engine (covering both the audit-manifest-enabled mode with encryption enabled and disabled and the audit-manifest-disabled mode where apply proceeds without journaling and rollback is unavailable), the bootstrap and sync modes with conflict resolution, `Sync_Attachment` upsert idempotency, the queue and background worker, and the multi-team batched metadata and issue retrieval, and THE System SHALL execute these integration tests without issuing any request to the real Linear API.
3. THE System SHALL provide a thin top layer of end-to-end tests validating the happy path and key gates of each user-facing surface: the CLI commands including the read-only guarantees and the confirmation and low-confidence gates, the `Sync_History_Server` URL routing with access control and not-found handling, the `MCP_Server` read-only tools and the gated opt-in mutating tool (confirmation key, accept-low-confidence argument, and fresh `Plan_Reference`), and the consumer-facing `CI_Enforcement_Action` pass and fail conditions.
4. THE System SHALL validate the executable correctness properties by property-based testing as a distinct required test type layered on the correctness-property methodology this specification already mandates, exercising each covered property over many generated inputs rather than fixed examples.
5. THE System SHALL cover by property-based testing at least the following properties: deterministic `Stable_UUID` derivation where identical inputs reproduce a byte-identical UUID; deterministic discovery ordering that is byte-for-byte identical across repeated runs over an unchanged tree; deterministic framework adapter selection over ambiguous path inputs; idempotent re-runs where durable-identity matching produces byte-identical results and creates no duplicate issue and no duplicate `Sync_Attachment`; rendering round-trip stability where parse then derive then render then parse reproduces the same final titles with no progressive `Feature_Name` prefixing; the maximum-weight one-to-one assignment with a deterministic tie-break; `Attachment_URL` idempotency where upsert-by-URL never duplicates an attachment on any page; and append-only history completeness where appending never modifies or deletes a previously-recorded `Sync_History_Event`, per-page rollover to a deterministic paged `Continuation_Attachment` preserves every entry across the attachment chain, and a rollback is recorded as an appended `rollback` event rather than by removing or rewinding any earlier entry.

11. THE System SHALL make its tests deterministic and hermetic, such that no test depends on real network access, real credentials, or wall-clock nondeterminism, consistent with the deterministic guarantees defined elsewhere in this specification.

### Requirement 29: Project CI/CD pipeline via GitHub Actions

**User Story:** As a maintainer of the `task-linear-sync` project, I want the project’s own build, test, and release automation implemented as GitHub Actions workflows, so that every change is validated across all surfaces and releases are produced safely and reproducibly.

#### Acceptance Criteria

1. THE System SHALL provide the `Project_CICD_Pipeline` as GitHub Actions workflows that build and validate all surfaces (the core library and CLI, the programmatic API, the `Sync_History_Server` web component, the `MCP_Server`, and the consumer-facing `CI_Enforcement_Action` package itself), WHERE the `Project_CICD_Pipeline` is the project’s own internal build, test, and release automation and is distinct from the consumer-facing `CI_Enforcement_Action` of Requirement 26.
2. WHEN a pull request is opened or updated, or a push lands on a main or protected branch, THE `Project_CICD_Pipeline` SHALL run dependency installation, lint, type-check, build, and the full test suite including the unit, integration, end-to-end, property-based, contract, and security tests defined in Requirement 28.
3. THE `Project_CICD_Pipeline` SHALL execute the tests defined in Requirement 28 as part of the pipeline run rather than deferring them to a separate manual step.
4. IF lint, type-check, build, or any required test fails, or IF measured coverage falls below the configured minimum threshold defined in Requirement 28, THEN THE `Project_CICD_Pipeline` SHALL fail the workflow with a non-zero, merge-blocking result.
5. THE `Project_CICD_Pipeline` SHALL run without requiring any real Linear credential or real organization identifier, relying on the hermetic tests of Requirement 28.
6. WHERE the `Project_CICD_Pipeline` uses secrets for publishing or other privileged steps, THE `Project_CICD_Pipeline` SHALL obtain those secrets from the CI platform’s secret store and SHALL NOT expose any secret value in any log or output, consistent with the security-screening posture of Requirement 10.
7. WHERE a release is performed, THE `Project_CICD_Pipeline` SHALL build the ECMAScript Module output and the TypeScript declaration files and publish the package with its declared entry points (the programmatic API entry point, the CLI binary, and the `<pkg>/mcp` subpath entry point) per Requirement 18.
8. WHERE a release is performed, THE `Project_CICD_Pipeline` SHALL verify by a distributed-defaults scan that the published defaults contain no real organization identifier, real token, or real UUID value, consistent with Requirement 17, criterion 10, and Requirement 18, criterion 7, and IF the scan detects any such value, THEN THE `Project_CICD_Pipeline` SHALL fail the release with a non-zero result and publish nothing.
9. THE `Project_CICD_Pipeline` SHALL install dependencies from a locked dependency manifest so that pipeline runs over unchanged inputs are reproducible and deterministic.
10. WHERE a Node.js version matrix is configured, THE `Project_CICD_Pipeline` MAY run the build and test suite across multiple supported Node.js versions, each at or above the minimum version required by Requirement 18.
